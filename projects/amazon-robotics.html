Finding a Month-Old Failure in a Production Robotic Vision System

Amazon Robotics · Robotics Data Scientist Intern · Sep – Dec 2025

This work is covered by confidentiality, so the description below stays at the level of method rather than system specifics.

The problem

A robotic vision system in production was failing intermittently. It had been doing so for roughly a month without an identified cause. Failures of this shape are genuinely hard: too rare to reproduce on demand, so you cannot attach a debugger and wait; too frequent to write off as noise, so you cannot ignore them. Conventional debugging had already been tried and had not converged.

Reframing it as a statistics problem

The insight was that the system had already recorded the evidence. Millions of production cycles had been logged, each with its conditions and its outcome. That is not a debugging problem — it is a hypothesis-testing problem, and the question is not "what went wrong in this trace" but "which conditions are the failures not independent of."

I applied chi-square and independence testing across the logged cycle population to find the conditions whose association with failure was too strong to be chance. At production scale, the sample size that makes the failure hard to reproduce manually is exactly what makes it easy to detect statistically — the rarity works in your favor once you stop trying to catch a single instance.

Cross-model consistency as a detector

Separately, I designed consistency metrics across the segmentation, depth, and dimension pipelines. The principle: these models observe the same physical scene through different representations, so their outputs are mutually constrained by geometry. Segmentation and depth should agree about where an object's boundary is; depth and dimension should agree about how large it is.

That yields a supervision signal without ground-truth labels. When the models disagree with each other beyond what their independent error rates would explain, at least one is wrong — and you learn this in production, continuously, without anyone annotating anything. I built these as scalable Python pipelines over AWS S3 and SQL.

Outcome

  • Root cause isolated in under two weeks — more than 50% faster than the preceding effort — which directly unblocked the engineering fix.
  • The consistency metrics became a production monitoring framework used for threshold tuning and alerting, so the class of failure is now caught rather than rediscovered.

Why this matters for deployed robots

A learned policy that works in the lab and degrades quietly in the field is the default failure mode of robot deployment, and it is rarely a dramatic crash — it is a slow drift in a perception input that nothing was watching. The transferable lesson here is that deployment monitoring has to be designed alongside the system, and that models which observe the same physical world can be made to check each other for free.
